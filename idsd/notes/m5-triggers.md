## 1. 边界：触发器 ≠ 判据

这条分工是 M5 的全部地基：

|  | 触发器 | 判据 |
| --- | --- | --- |
| 回答 | **要不要查** | **查到什么算数** |
| 性质 | 调度决策 | 语义判断 |
| 能否用廉价启发式 | ✅ 能 | ❌ 不能（必须可复算） |

S7 立下的「阈值是运气不是判据」约束的是**判据**。触发器是**调度**：误触发只多花一次廉价查询，
漏触发只是维持现状。所以这里允许便宜——但必须把「便宜到什么程度、代价是什么」写清（见 §4）。

## 2. 四个口子

| 钩子 | 时机 | 锚（query 位） | 证据（task 位） |
| --- | --- | --- | --- |
| H1 起手查 | Plan 入口 | 探到的实体名 | 任务描述 |
| H2 卡壳查 | 报错 / 重试 | 错误信息里的实体名 | 错误 + 上下文 |
| H3 回想查 | 上下文命中图实体 | 命中实体名（必然非空） | 当前上下文 |
| H0 显式点名 | 随时 | 实体名；没有就点名原文 | 点名文本 |

自动的只有 H1/H2/H3；**H0 是逃生口**，不占总闸（用户点名必须响应）。

**为什么锚位用实体名而不是整段文本**：M1 的双文本改造就是这么约定的——`query` 位放"短锚"、
`task` 位放"证据"。把任务原文同时塞进两位会直接触发 `texts_equal` 退化（探针 B §4 那个坑），
证据层塌成空，而且会退回人类面语义——**白花一次 LLM 生成答案**。
所以钩子先探实体、拿实体名当锚；**探不到就不查**（记 `skipped="no_entity"`）。

这条比设计文档（「H1 anchor=任务描述」）严一格，是有意的：设计写的时候还没做双文本改造，
没算过退化代价。实测无实体 H1 退回人类面后：`degraded=true, reason=texts_equal`，
cited 出 5 个实体、`answer_context` 533 token，里面全是周杰伦/台北/腾讯——
既烧了一次 LLM，又往上下文里灌了噪声。漏查只是少一次助攻，H0 随时可补。

## 3. H3 的探针为什么不建 Aho-Corasick

需求是「当前上下文里字面命中图上已有实体名」，不是全库多模式替换。用首字分桶就够：

```
桶: 首字 → 该字开头的名字（按长度降序）
扫描: 文本每位置查桶 → 命中最长者 → 跳过其长度
```

- 复杂度 ≈ O(文本长度 × 桶内候选数)，个人库规模（几百~几千节点、上下文几千字）微秒级；
- 顺手解决了「张三」vs「张三丰」的抢位问题（同位置优先吃最长的）；
- 不引第三方依赖。真到上万实体再换 AC 自动机，接口不变（`probe.replace(names)`）。

## 4. 总闸：拦下但不沉默

`SessionGate(limit)` 只管「查几次」。规则四条：

1. **只有真正发起 `memory.search` 才扣一格**——被拦下、探不到实体都不算「查过」；
2. **拦下是正常路径，不是异常**：返回 `skipped="gate_exhausted"` + 事件；
3. **H0 免扣**：`exempt=true`，总闸为 0 也照查；
4. **探不到实体也不扣**：`skipped="no_entity"`（见 §2）。

事件（`engine.trace()`）字段：
`hook / hook_name / phase / anchor / entities / queried / skipped / hit / degraded / reason / gate_left / exempt / context_tokens / spill`。
「这次为什么没想起」与「为什么想起」看到的是同一张表。

## 5. 失败不会带崩正在干的活

`memory.search` 抛异常时：记 `hit=false, reason="search_error:<类型>"`，返回 `result=None`，
继续干活。记忆是助攻，不是依赖——这条和 M3 的「取不到就报 missing 不编」是同一个态度。

## 6. 真机冒烟（真图 17 节点 / 16 边）

```
$ python -m graphkb.cli trigger plan "帮我整理张三的入职材料，顺便核对北京那边的社保"
probe_size=17  hook=H1  entities=[张三, 北京]  anchor="张三 北京"
queried=true  hit=true  degraded=false  gate_left=4  context_tokens=295
```

`hits.entities` 里 张三 的 `origin` 是 `mixed`（早期手工编辑过）——M4 的溯源在触发器路径上也生效。

**同一次冒烟暴露的问题（当天已修）**：注入里曾混进 4 个与锚点无关的块（李雷在腾讯 / 周杰伦在台北）。
原因是 `memory_api` 把 `trace.chunks` 全量交给 Inline&Spill，预算够就全进 `answer_context`。
这与 S7 那条不变量是同一个道理的反面案例——「命中必须落在问题核心实体的连通分量内」。

修法：块只在与命中实体/关系的 `source_id` 有交集时才进注入（`provenance.chunk_ids` 已经算好了，
不用额外查询）；其余仍在 `hits.chunks`，标 `linked=false`，并在 warnings 里明说多少块被挡在外面。
溯源读不到时不饿死注入：退回全量、`linked=null`（不知道 ≠ 无关）。
实测同一句 H1：295 → **247 token**，李雷/周杰伦两块不再进上下文，而北京那一块（李四的文档）
留下来——因为「北京」确实是从那块里抽出来的，这是对的。

## 7. 边界

- **H3 盲区**：语义相关但字面无重叠 → 漏查（少一次助攻，不是错误）。
- **K 是经验值**：5 是起点，图/库变大后可调；它是调度预算，不是判据。
- **H1 锚文本质量**：任务描述太长会把锚稀释——调用方（harness）该传精炼的任务描述；探针探到实体时不受此影响。
- **并发**：多钩子齐发时，同 workspace 的写侧串行化仍归 M6。
- **跨 Agent 触发**（"隔壁刚解过这个"）属 L3，后置。
