# 检索命中判据与高亮编码的演进全记录

> 范围：S7「检索可视化闭环」从 2026-08-17 落地到 2026-08-30 定型的**全部五轮返工**，以及为它铺路/绊腿的 S3/S5 遗留。
> 为什么值得单独记：目前这套「看起来比较合理」的状态，是被用户当场驳回四次错误判断之后换来的。这些驳回理由比最终代码更贵——不写下来，下一次改动（尤其是图变大之后）大概率会重犯同一批错。

## 1. 背景：为什么"命中了什么"这件事天生模糊

LightRAG 的 dual-level 检索（`lightrag/operate.py::_perform_kg_search`）三路并行：

| 输入 | 打到哪个库 | 语义 |
|---|---|---|
| `query` 原文 | chunks VDB | 文本块相似 |
| `low_level_keywords`（问题里的具体实体名） | entities VDB | **实体名 + 描述**的向量相似 |
| `high_level_keywords`（问题的主题抽象） | relationships VDB | 关系/主题相似 |

两个后果决定了后面所有的坑：

1. **`QueryParam.top_k` 默认 40、`chunk_top_k` 20**。本项目图很小（17 实体 / 16 关系），所以每次检索在物理上就是"把全图捞进上下文"。**检索层面根本不存在"命中区分"**——全捞。
2. **实体向量库 embed 的是"名字 + description"**，而 description 是 LLM 自由文本。于是描述里的词会污染召回：问「腾讯」能把「字节跳动」拽进来，只因它的描述写着"总部位于北京"。

因此 S1 定下的硬约束（约束 2）说"可视化 = 给检索器加透明窗，不发明新检索算法"，实际含义是：**"答案落在哪"必须由展示层自己判定**，LightRAG 不会替你判。这个判据就是本文五轮返工的全部内容。

还有一点要认：因为 `mix` + `top_k=40` 意味着 **LLM 确实看到了全图**，所以透明窗展示的"路径"是对相关性的**事后重构**，不是执行时的因果轨迹。我们做的是"哪些点真正支撑了答案"，不是"模型注意力去过哪里"。这句话必须写在文档里，否则后来者会以为高亮集是模型的输入集。

## 2. 五轮演进全记录

### 第 0 轮：初版（`a26979c`，08-17 00:56）

- 后端 `GET /api/query`：`aquery_data` 拿结构化上下文 → `trace = {keywords, entities, relationships, chunks}`，实体分数由 `_score_trace` 补。
- 前端：检索框 + `renderQueryHighlight()`；多轮颜色 `ageColor()` = **同一色相按轮次变浅四档**。
- 隐含假设：**trace 里的实体 = 命中的实体**。这条假设是后面所有麻烦的根。

### 第 1 轮：四个 bug 与"小图全连通"这个错判（`3049498` + `2aa5c68`，08-18 00:28）

用户验收原话（附两张截图）：

> 上传后图不马上变 / 检索后界面难看 / **全部节点边泛红** / 多轮颜色无变化。S7 没有一个正确，请仔细检查。

定位与处理：

| 症状 | 根因 | 改法 |
|---|---|---|
| 上传后图不变 | `ainsert` 同步耗时实测 28.3s，前端无反馈 | 按钮禁用 + 「解析中…」+ 预计 20–30s 提示 |
| 界面难看 | 整段答案塞进顶部 `#status` | 左下角 `#answer-panel` 浮层 + Markdown 渲染 |
| 全图泛红 | trace 是"发给 LLM 的上下文子图"，小图 ≈ 全图 | `_score_trace` → `HIT_TOP_K=5` + `_hit_trace`（只高亮 ll_keywords 的向量 top5 + 其扩散） |
| 多轮无变化 | 前端只留最后一轮 | `queryRounds`（上限 4）+ `hitAge` 驱动色阶 |

**我当时补了一句错误的解释**：「小图上下文几乎全连通，所以全红」。用户当场驳回：

> 不对，小图没有全连通，李雷->腾讯->深圳 是独立的，不应该检索出来呀，再检查看看。

脚本实测证明图有 **3 个连通分量**（张三分量 9 节点 / 李雷-腾讯-深圳 3 节点 / 姚明测试分量 4 节点），我的"全连通"纯属未验证的顺口解释。真因更正为两条：**全局向量 `top_k=40` 不看连通性**，以及**关系向量检索会命中"话题相似但实体无关"的跨分量关系**。

> 教训：症状和根因之间不要跳步。我那次是为了让解释尽快闭环而编了个听起来合理的机制，结果它把下一轮修复引偏了一整轮。

### 第 2 轮：跨分量误标红 → 核心实体 + 1 跳图扩散（`9e27c37`，08-18 00:52）

用户再次驳回"已修好"：

> 「张三在哪工作」的结果里为什么"李雷"会被标红圈？「字节跳动总部在哪里」为什么会标红"腾讯->深圳"？看来检索还是有问题，再检查。

我先怀疑是 LightRAG 的算法问题，于是把纯向量方案能试的都试了一遍：用 question / hl_keywords / ll_keywords 当查询文本、变 top_k、变阈值、改 `mode=local`——**没有一种能区分"实体相关"与"话题相似"**。「腾讯→深圳」和「字节跳动→总部在北京」在关系向量空间里就是一对近义词。

结论：不能靠换查询文本救，必须引入**图结构**。改法：

```
核心实体 = entities_vdb.query(ll_keywords 拼接, top_k=5)
高亮     = 核心实体 ∪ 与核心实体相连的边 ∪ 这些边的另一端
```

效果（当时的实测）：「张三在哪工作」命中 8 实体全在张三分量，「字节跳动总部在哪里」9 实体全在字节分量。用户第三轮复验通过颜色之外的部分。

> 注意这一步已经隐含了正确方向（**用连通性组织命中**），但我只把它用在"扩散"，没敢拿它当"取舍"——于是留下了第 3 轮的病。

### 第 3 轮：多轮色阶太怂 → 拉开色阶（`d6166da`，08-30 12:00）

用户：

> 上面第 3 步，张三那 8 个好像不是浅粉，还是红色呀，你检查看看呢。

查（用 `browser` evaluate 读 cytoscape 实际值，见 §6）：轮次记录是对的，`hitAge` 确为 1；错在色阶第 2 档 `#e05a6a` 与第 1 档 `#c81e2e` **色相几乎相同**，小尺寸细环上肉眼都是"红"。

改法：`#c81e2e → #ef8a96 → #f7c3ca → #fbe2e6` 四档拉开，并同时变细（5→1.5px）、变小（40→32）、变淡（opacity 1→0.46），右下角加图例；`server.py` 加中间件对 `*.html` `/` `/api/*` 下发 `Cache-Control: no-cache`（此前改完前端浏览器死咬旧 JS，我自己也被这个坑到）。

> 这一轮方向对了一半：**确实该多维编码**，但我选的三个维度（浅度/细度/透明度）**全都住在同一根"显眼度"轴上**，互相抵消。第 5 轮才看清这一点。

### 第 4 轮：分数闸门——一个当时以为能收尾的补丁（`9e30cf7`，08-30 13:02）

用户：

> 我追加了个"腾讯总部在哪"的检索，为什么把"字节跳动"相关的也检索出来了呢……检索算法还是有问题呀

实测该题：keywords 抽取完全正确（`ll=["腾讯"]`、`hl=["总部地址"]`），但 `entities_vdb.query("腾讯", top_k=5)` 返回：

```
腾讯 0.7594 | 深圳 0.6778 | 李雷 0.6260 | 字节跳动 0.4875 | 张一鸣 0.4614
```

后两个是跨分量噪声——因为字节跳动的描述里有"总部位于北京"。17 个实体硬取 top5 必然捞到它们，再经 1 跳扩散点亮整串（北京/李四/张三/南开大学 + 5 条边）。

我写了个探针跑 7 题 × 2 种查询文本，实测分数分布：同分量候选普遍是最高分的 82%–95%，跨分量噪声普遍 55%–73%，中间有天然断层。于是加了 `HIT_MIN_RATIO = 0.8` 闸门（低于最高分 80% 的既不进核心也不参与扩散），并把排除过程回显到面板（「字节跳动 0.487（仅最高分的 64%）」）——至少不藏着。

### 第 5 轮：用户否掉闸门 → 判据与编码同时换血（`9735ab4`，08-30 17:52）

用户没有报 bug，而是提了一个更根本的问题：

> 感觉还是有些问题，不好说这种排除对不对。难道不先考虑连通性吗？还有，一个问题的答案涉及的图谱上的点和线不应该是一个连通图吗？有什么例外场景吗？先思考一下，不用急着改代码。

为了不把思考悬空，我跑了三道探针题，每道都直接改变了一个设计决策：

| 探针 | 结果 | 推翻/确立了什么 |
|---|---|---|
| 「蔡依林和周杰伦是什么关系」 | 答案主语「台北」与最高分的比值**正好 0.80**，卡在闸门边界上活下来（还是靠图扩散捞的） | **推翻闸门**：阈值是运气不是判据，一次 embedding 抖动就能把答案依赖的点踢掉 |
| 「腾讯和字节跳动的总部在哪个城市」 | 高亮横跨两个不相连分量（腾讯→深圳｜字节跳动→北京），中间确实没有边 | **推翻"连通性当筛子"**：按"只留 top1 所在分量"筛，会砍掉对比题答案的一半 |
| 「张三认识姚明吗」 | 图里没有姚明，LLM 诚实答"无法确认"，但透明窗把张三整个分量染红 | **确立"连通性不充分"**：一片连通的簇照样可以是假的证据 |

于是把两件事同时改掉：

**判据**——删掉闸门，改成两个可复算的结构判据：

```
锚点 = 问题文本里字面出现的图实体名          （零参数）
证据 = 答案文本里字面引用的实体名 + 连接两者的全部等长最短路   （连通性由构造保证）
仅召回 = 向量捞到但两者都不是 → 图上不着色，进候选列表带分数展示
分数 = 只做候选排序 + 无锚点时兜底（兜底要显式标 anchor_mode=vector_fallback）
```

**编码**——把两个语义维度拆到不打架的通道上（详见 §5）：证据层→形态，轮次→色温，第几轮→角标数字。

用户在此之前还追问了一句关键的话：

> 三态分层这个思路对，但颜色上是不是有些混乱，浅红不是用来区分上一轮，哦，上一轮好象是浅粉，浅红、浅粉区别明显吗？

把四档算成画布上的实际合成色才看清问题（§5 的表）。**结论：不是我档位给少了，是三个状态挤在一根轴上挤不下。**

## 4. 沉淀下来的判据与不变量

**不变量（正确表述）**

> 一个问题的答案 = **若干个连通簇**。簇内必须连通；簇数 ≈ 问题里独立实体的个数（通常 1，对比题 2）。跨簇"无路径"是**信息**，不是要抹掉的噪声。

最初我把它写成"一题答案应当是一个连通图"，太硬。用户提问里的这句"不应该是一个连通图吗"配合例外清单，才逼出上面这个更准的版本。

**为什么不能拿连通性当筛子（两个方向都会失效）**

- 太狠：对比题/并列题/否定题天然多簇，按 top1 分量筛会静默丢半边答案。
- 太松：个人库长到各主题互相关联后，整图容易退化成一个大分量，此时"按分量筛"等于不筛。

所以连通性放在**构造**位置（锚点之间怎么走得到），不放在**筛选**位置。

**例外场景清单（已实测或已推演，做后续改动时逐条对照）**

1. 对比/并列题 → 多簇合法（实测：腾讯 vs 字节跳动总部）。
2. 图上无此实体 → 必须显式报「图上没有对应实体」，不能拿向量最近邻冒充（实测：姚明）。
3. 答案需要 2 跳以外 → 1 跳扩散够不着，必须走最短路（实测：台北、南开大学 3 跳）。
4. 0 跳答案 → 高亮退化成孤立一个点，无环可画，属正常。
5. 代词/省略的第二轮提问 → 字面锚点失效，只能退向量 top1 兜底，**这一步天生不可靠，必须标注**。
6. 属性型问题 → 属性被 LLM 揉在 description 自由文本里（backlog 条目 7），点线层面信息量低。
7. 别名未对齐 → 本该连通的被切成两簇；此时"无路径"提示的是图的缺陷（该合并），不是检索失败。这条把 S5 的合并能力和透明窗接上了。

**分数该放哪儿**

分数继续算、继续显示，但只回答"为什么认为它是答案主体"，**不回答"谁不算"**。取舍交给字面锚定 + 图上路径——这两样都能指着解释。

**分层而非二态的意义**

用户的不适（"不好说这种排除对不对"）本质是 UI 只给了红/灰两态，于是"被排除"看起来像"被否定"。改成三态 + 候选列表全带分数之后，**判断权回到用户手里**，我不再替用户当法官。这与项目最初的"透明"诉求是同一件事。

## 5. 可视化编码：通道预算

**为什么四档粉不行（2026-08-30 实测，非估算）**

旧方案 = 色阶变浅 + 元素 opacity 衰减，画在 `#fafbfc` 画布上的合成结果与对比度：

| 轮次 | 定义色 × opacity | 合成色 | 对比度 |
|---|---|---|---|
| age0 本轮 | `#c81e2e` × 1.00 | (200,30,46) | **5.51** ✅ |
| age1 上一轮 | `#ef8a96` × 0.72 | (242,170,179) | 1.82 ⚠️ |
| age2 | `#f7c3ca` × 0.58 | (248,219,223) | 1.26 ❌ |
| age3 | `#fbe2e6` × 0.46 | (250,240,242) | 1.08 ❌ |

非文字图形可辨下限约 3:1 ⇒ **四档里只有两档真看得见**。而且元素级 `opacity` 会把标签文字和类型填充色一起洗淡，历史轮的点连"是人是公司"都读不出来。

**通道分配（现行）**

| 语义维度 | 通道 | 具体值 |
|---|---|---|
| 证据层（锚点 / 引用 / 路径） | **形态** | 锚点＝粗实环 4.5px + 标签加粗；答案引用＝虚线环 2.5px；路径中间点＝虚线环 2px；边 `line-style` 按 direct / path |
| 轮次（本轮 / 更早） | **色温** | 本轮 `#c81e2e`，更早 `#5b6b82` |
| 第几轮（精确序） | **文本** | 标签角标 ¹²³ + 图例行 |
| 未命中 | 淡化 | `.dimmed` opacity 0.2 |
| 仅召回 | **不上图** | 只在答案面板「捞到未用」折叠列表里，带分数 |

要点：**人眼判"红 vs 灰蓝"是可靠的二值判断，判"三种浅粉"不可靠**；"第几轮"这种精确信息交给角标和图例，比交给色阶便宜且不会错。层级与轮次分住两个正交通道，才装得下 3×2=6 个状态。

**一条自检法**

> 图例里两块色并排放着看不出区别，就说明这个编码本身不成立——不是"用户没仔细看"。

## 6. 验证方法（可复用，含工具坑）

| 要做的事 | 办法 |
|---|---|
| 确认前端渲染真值 | `browser` + `act kind=evaluate`：`document.getElementById('cy')._cyreg.cy` 拿到 cytoscape 实例，用 `ele.pstyle('border-color').value` / `pstyle('border-width').pfValue` 读**渲染值**（`ele.style()` 只会拿到函数映射本身）。cytoscape 在 `container._cyreg.cy` 上挂了实例（`cytoscape.cjs.js:19880`） |
| 驱动一次检索 | 在 evaluate 里设 `#query-input`.value 后 `#btn-query.click()`；单次 evaluate 内等待别超过 ~12s，长任务改成"点完→PowerShell sleep→再 evaluate 读" |
| 判断高亮集合是否越界 | 直接打 `/api/query`，比对 `trace.retrieved`（上下文原记录）与 `trace.entities`（高亮集）——高亮必须是上下文的子集 |
| 分数分布探针 | 写一次性脚本遍历 N 题 × 查询文本，dump `entities_vdb.query()` 的 distance；比推理"阈值该定多少"可靠（也是它证明了阈值不可靠） |

踩过的坑（都还会再踩）：

- **视觉模型在本窗口不可用**（`vision model ... does not support image input`）⇒ 所有 UI 结论只能靠读计算样式，**观感判定完全依赖用户眼睛**。所以凡涉及颜色的结论必须给数字。
- 浏览器死缓存旧 JS ⇒ 靠 `Cache-Control: no-cache` 中间件 + `?v=N` 双保险。
- PowerShell 5.1 用 `Add-Content` 写中文会产出 GBK 字节破坏 UTF-8 源文件（曾让 vite 构建报 `error at src/main.ts:3:8`）⇒ 中文内容一律走 `write`/`edit` 工具。
- 在 `site-packages/lightrag` 目录下跑 `python -c` 会撞 `types.py` 与标准库同名 → circular import。
- holdout 场景引用业务模块的私有函数（`_score_trace`）会**静默腐烂**：`3049498` 删掉该函数后 S3 考卷连续 12 天全废，无人发现。

## 7. 当前实现

```
_hit_trace(rag, question, answer, trace):
  pool            = trace.entities[].name ∪ relationships 端点         # 高亮不得越出上下文
  score_by_name   = entities_vdb.query(ll_keywords or question, top_k=5).distance   # 只作旁证
  anchors         = 字面出现在 question 里的 pool 名（长名优先，被长名包含的短名不重复计）
  cited           = 字面出现在 answer 里的 pool 名 − anchors
  anchor_mode     = literal | vector_fallback(pool 内最高分) | none | vdb_error
  adjacency       = 全图 get_all_edges() ∪ 上下文边（无向，按弱连通语义）
  对锚点两两求最短路；对每个 cited 连到最近的锚点
      · 记全部等长最短路（≤ MAX_HOPS=4，≤ MAX_PATHS=6）
      · 连不上 → 记入 disconnected（不静默丢弃）
  layers          = anchor > cited > path；边 layer = direct（两端都是 target）| path
  recall_only     = pool − 高亮（带分数）
  unmatched_keywords = ll_keywords 中图上查无此名、且无法包回已命中名的
降级：vdb_error / no_anchor → 保留全上下文、layer=None、score=None，不假装分层
```

`trace` 字段：

| 字段 | 含义 |
|---|---|
| `keywords` / `chunks` / `processing_info` | 同 S1/S3，原样保留 |
| `entities[]` | **高亮集**：`name/type/description/score/layer` |
| `relationships[]` | **高亮边**：`src/tgt/description/keywords/weight/score/layer` |
| `retrieved` | 检索器捞到的**原记录**（count + 名单），不受分层影响，用来分辨"没捞到"与"捞到了但答案没引用" |
| `hit_layers` | `anchor_mode/anchors/cited/paths[]/disconnected[]/recall_only[]/unmatched_keywords/top_k/max_hops/max_paths` |

参数表（都是**展示预算**，不是语义筛子——超限一律"如实报"，不做静默取舍）：

| 常量 | 值 | 越界行为 |
|---|---|---|
| `HIT_TOP_K` | 5 | 只影响候选列表长度与兜底锚点选取范围 |
| `MAX_HOPS` | 4 | 超过则记 `disconnected`，不硬连 |
| `MAX_PATHS` | 6 | 等长路多于 6 条则截断，并在面板标「等长 N 条」 |

测试与考卷：pytest **51 passed**；S3 / S5 / S7 holdout 各 **7/7**。S5 场景的断言源已从 `trace.entities` 改绑 `trace.retrieved`——理由：S5 承诺的是"编辑会反映到检索结果"，那是检索层的事实，不该依赖 LLM 措辞（mock 答案不引用任何实体时，绑高亮的断言会假失败）。

## 8. 残留风险与未做

1. **高亮跟着 LLM 措辞走**：答案改用代词或换说法（只说"他在北京"），该实体就不进红圈。靠"捞到未用"列表兜住可见性。
2. **字面匹配会误引常见词**：实体"北京"被"北京人"命中。17 节点小图上无害，图变大后需复核。
3. **假信心红圈未做判定**：「张三认识姚明吗」那种"答案在复述已知而非给证据"，目前只提示 `unmatched_keywords`；判它需要否定语义 = 新规则族，按约束 6 需用户拍板 → [backlog 条目 12](../backlog.md)。
4. **`MAX_HOPS`/色温二档等均未做可配置**。
5. **孤立实体不被 dual-level 召回**是 LightRAG 固有边界（backlog 条目 4，用户已拍板暂不处理）。
6. 图长成一个大分量之后，"簇数"这个信号会退化——届时"锚点 + 答案引用"仍是唯一有区分力的判据，这也是当初不选"纯向量"而选"锚点+路径"的核心理由。
7. 若将来想拿到**忠实的执行轨迹**而非事后重构，就得真去收窄检索本身（`mode`/`top_k`），那会擦到约束 1（图引擎复用 LightRAG）的边，需要单独立片讨论。
