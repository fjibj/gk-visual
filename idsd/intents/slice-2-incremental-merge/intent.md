# Intent: slice-2-incremental-merge（增量合并 + 实体对齐）

> 本切片是总体意图 Goal 2 的落地，关闭 Failure Conditions 1（重建整库）与 4（实体对齐失败）。
> 前置：S1 已交付单篇文档 → 图 + 检索 + 结构化 trace。本切片在此基础上做"第二篇及以后"。

## Goal

让第二篇文档并入既有图时**不重建整库**，且**同一实体正确对齐**（同名自动去重、变体可显式合并），对齐过程/结果可见。

三个验收点：

1. **增量**：摄入两篇文档后，图是累积的（实体/关系 = 两篇并集），第一篇的实体不消失、不整库重建；
2. **自动对齐**：两篇文档中**同名**的实体合并为**一个**节点（复用 LightRAG ingest 的 `entity_name` 聚合）；
3. **显式对齐 + 可见**：提供命令把**变体实体**（如"张一鸣" 与 "张一鸣（字节创始人）"）显式合并，合并后源被删、关系转移到目标，返回结构化结果（转移关系数等），检索随之命中合并后的实体。

## Constraints

1. **复用 LightRAG**：增量靠 `ainsert`（pipeline 天然增量，不自己写合并逻辑）；显式合并封装 `rag.amerge_entities`（SDK 核心方法，不碰 HTTP）。
2. **对齐结果可见**：合并操作返回结构化结果（删除的源、转移的关系数、目标终态）——延续 S1 的 trace 暴露口，为 S3 渲染备料。
3. **纯 Python + CLI + pytest**：本切片仍不引入前端/HTTP 服务。
4. **规则预算 ≤ 1**：不新增"规则族"——同名对齐是 LightRAG 现成聚合，显式合并是人控操作（不是自动规则）。

## Failure Conditions

1. 摄入第二篇文档后，第一篇的实体/关系消失或图被重建 → 增量失败。
2. 两篇文档中的同名实体在图中出现为**多个节点** → 自动对齐失败。
3. 显式合并后：源实体未删除、或关系丢失、或检索仍命中旧名 → 显式对齐失败。
