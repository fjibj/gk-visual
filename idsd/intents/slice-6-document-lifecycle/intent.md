# Intent: slice-6-document-lifecycle（文档生命周期闭环）

> 本切片把「文档」补成知识库的一等公民：上传→图、列表、删除→图收敛。
> 硬依赖：S1（文档→图）、S4（前端）；顺序上排在 S5（编辑回路）之后收尾。
> 上传复用 S1 `ingest_document`（`ainsert`），删除复用 LightRAG `adelete_by_doc_id`。

## Goal

让用户从浏览器直接管理文档：把文档丢进来长出图、看到库里有哪些文档、删掉文档时图正确收敛。

三个验收点：

1. **上传 → 图**：浏览器上传文档（文件/粘贴文本）→ 后端复用 S1 ingest → 图长出（实体/关系增加，可即时看到）；
2. **文档列表可见**：能列出库里的文档（含各自贡献的实体/关系数），体现「文档如何变成图」的透明；
3. **删除 → 图收敛**：删除某文档后，只属于它的实体/关系被清掉，被多文档共享的实体正确保留（不收敛过度），检索不再命中已删文档独有的实体。

## Constraints

1. **复用 LightRAG**：上传走 `ainsert`（S1 `ingest_document`），删除走 `adelete_by_doc_id`（已内置「部分受影响实体用剩余文档缓存重建」），不自己发明删除/收敛逻辑。
2. **删除结果可见**：删除操作返回结构化结果（删了哪个文档、图里实体/关系如何变化），延续 trace 暴露口。
3. **前端 + 后端**：复用 S4 前端，新增文档管理界面 + 3 个 API（上传 / 列表 / 删除）。
4. **规则预算 ≤ 1**：不新增规则族——上传 = ingest，删除 = LightRAG 现成删除，收敛 = 其内置重建。

## Failure Conditions

1. 上传文档后图没长出（实体/关系未增加）→ 上传失败。
2. 删除文档后，只属该文档的实体/关系仍残留（孤儿）→ 删除不干净。
3. 删除文档后，被多文档共享的实体被误删 → 收敛过度。
4. 删除文档后检索仍命中已删文档独有的实体 → 删除没闭环。
