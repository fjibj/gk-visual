## 3. 文档版本更新 + 多版本并存

- **状态**：S6 范围内的待定设计点，未定（用户 2026-08-16 提出）。
- **现状查证（LightRAG doc_id 机制，`pipeline.py:933-949`）**：
  - `ainsert(ids=…)` 支持**显式传入文档 ID**——这是版本管理的钥匙。
  - 不传 ids 时：有 file_path → `doc-` + md5(路径)（同路径=同 id）；纯文本 → `doc-` + md5(内容)（内容变=新 id）。
  - 内置**重复检测**：同文件名 / 同内容 hash 会被判 duplicate 跳过，不重复 ingest。
  - 当前 `ingest_document(rag, text)` 只传文本 → doc_id=md5(内容)：内容一改就当**全新文档**（多版本悄然并存，旧版独有实体不消失，同名实体聚合）。
- **待定决策点**：
  1. 文档身份用什么定（文件名/路径 vs 内容 hash vs 显式 id）？
  2. 同文档重传语义：覆盖更新（旧版图收敛到新版）vs 只增新版（并存）vs 版本历史（保留 v1/v2 可回看）。
  3. 多版本并存是否需要元数据层（版本号/父文档/时间戳）？
- **建议**：覆盖更新优先（改文档→知识库反映最新版是基本预期），版本历史后置到 backlog 后续考虑；实现路径疑似 `adelete_by_doc_id(旧) → ainsert(新, ids=稳定id)`，需 spike 验证 LightRAG 的 duplicate 检测是否拦同 id 重插。
